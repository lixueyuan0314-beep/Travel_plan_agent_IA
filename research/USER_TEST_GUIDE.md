# 旅行规划 Agent 用户测试执行包

## 1. 研究目标

验证旅行规划 Agent 是否能让目标用户：

1. 看懂系统生成的交通与住宿组合方案；
2. 理解并使用“推荐—确认—执行”的授权机制；
3. 根据预算、换乘次数和速度偏好调整推荐结果；
4. 在信息缺失或外部服务异常时理解系统反馈并继续任务；
5. 对产品的可用性、可控性和可信度形成正向评价。

本轮建议招募 5–10 位参与者，用于发现主要可用性问题。样本较小，结果用于产品迭代，不用于推断总体市场比例。

## 2. 招募话术

> 你好！我正在测试一款“AI 旅行规划助手”，希望邀请你完成一次约 20 分钟的线上体验。测试对象是产品，不是你的能力；过程中没有标准答案。我们会记录任务是否完成、耗时以及你的意见，不收集密码、证件号、支付信息或其他敏感信息。你的反馈仅用于课程/求职项目改进。你是否愿意参加？

建议优先招募近一年内自行规划过跨城市旅行、使用过携程/Google Maps/铁路或航班平台的学生或年轻职场人。参与者不需要有编程背景。

## 3. 测试前说明（主持人照读）

> 感谢参加。今天测试的是产品，不是你。请一边操作一边说出你看到什么、期待什么、为什么点击某个位置。除非你完全无法继续，我不会马上给提示。请不要输入真实姓名、账号、支付信息或 API Key。每个任务最多 3 分钟。你可以随时停止测试。

确认参与者同意后，在记录表中将“同意参与”选为“是”。

## 4. 五个测试任务

### T1 生成并核对方案

> 你计划明天从巴黎前往里昂。请使用自然语言生成一份交通与住宿组合建议。在执行任何外部操作前，指出页面上显示的出发地、目的地、日期、推荐交通方式和需要你确认的内容。

观察重点：是否找到输入入口；是否看懂推荐；是否在未确认前误以为系统已经预订。

成功标准：生成方案，并正确说出至少 4 项关键信息及确认状态。

### T2 用约束筛选方案

> 预算上限为 80 欧元，最多接受 0 次换乘。请调整条件并找出最符合要求的方案，然后解释它为什么排在前面。

观察重点：是否找到预算和换乘设置；是否理解排序解释。

成功标准：完成约束设置，找到符合条件的结果，并给出与预算/换乘相关的解释。

### T3 改变排序偏好

> 现在你更在意速度。请把偏好改为“最快”，比较调整前后的首选方案，并说出发生了什么变化。

观察重点：能否发现偏好控件；是否理解推荐随偏好变化。

成功标准：成功切换偏好，并指出首选方案或排序理由的变化。

### T4 处理信息不完整

> 假设你只输入“帮我去里昂，时间还没定”。请观察系统如何处理缺失信息，并尝试根据提示继续完成规划。

观察重点：错误提示是否具体；用户是否知道下一步补充什么；系统是否避免直接执行高风险操作。

成功标准：识别缺失字段，并通过补充信息或安全回退继续任务。

### T5 验证异常恢复

> 打开“可靠性实验室”，运行“首次超时、重试成功”的场景。请说明系统尝试了几次、最终是否恢复，以及页面中哪些信息帮助你理解结果。

观察重点：恢复状态是否易懂；用户是否能区分“失败”与“重试后成功”。

成功标准：运行场景，正确说出尝试次数、最终状态和恢复原因。

## 5. 记录规则

- 主持人念完任务后立即开始计时。
- 达到成功标准时停止计时；超过 180 秒仍未完成，记录为“失败”。
- 结果分为：
  - **独立完成**：没有主持人提示；
  - **提示后完成**：主持人提供方向性提示后完成；
  - **失败**：超时、放弃或核心目标未达到。
- “提示次数”只记录主持人给予的帮助，不记录参与者自己查看页面提示。
- “错误次数”记录明显偏离目标且需要回退的操作。
- 尽量逐字记录关键原话，尤其是困惑、信任和确认相关表述。

建议的最小核心指标：

- 独立完成率 = 独立完成任务数 ÷ 已尝试任务数；
- 总完成率 =（独立完成 + 提示后完成）÷ 已尝试任务数；
- 平均耗时 = 已尝试任务的平均完成/终止时间；
- 平均易用性、可信度、有用性评分（1–5 分）；
- 平均推荐意愿（0–10 分）；
- T5 异常恢复理解率 = T5 独立完成或提示后完成的人数 ÷ T5 尝试人数。

## 6. 测试前问题

1. 过去一年你大约自行规划过几次跨城市旅行？
2. 你是否使用过 AI 助手规划旅行？使用过哪些？
3. 你对 AI Agent 的熟悉程度是 1–5 分中的多少？
4. 开始前，你对 AI 自动组合交通和住宿方案的信心是 1–5 分中的多少？

## 7. 测试后问卷

请按 1（非常不同意）到 5（非常同意）评分：

1. 我能轻松完成主要规划任务。
2. “推荐—确认—执行”流程让我感到操作可控。
3. 我能理解方案为什么被推荐。
4. 当信息缺失或服务异常时，我知道下一步该做什么。
5. 我愿意信任该工具提供初步旅行建议。
6. 该工具对规划跨城市旅行有用。

另请回答：

- 你向朋友推荐这款工具的可能性是 0–10 分中的多少？
- 最困惑或最不满意的地方是什么？
- 最有价值的功能是什么？
- 如果只能改一个地方，你希望改什么？

记录表中的“易用性”“可信度”“有用性”分别对应上面第 1、5、6 题。其余题和开放题可写入备注或另行保留原始问卷。

## 8. 主持人提示语

只在参与者停滞约 30 秒后使用，由弱到强：

1. “你现在期待页面发生什么？”
2. “页面上有没有和这个目标相关的区域？”
3. “你可以看看偏好/可靠性相关的设置。”

一旦提供提示，就把该任务结果记录为“提示后完成”或“失败”，不能再记为“独立完成”。

## 9. 结束语

> 测试结束了，谢谢你的反馈。刚才遇到的问题反映的是产品需要改进，不是你的操作问题。我们不会在项目材料中公开你的姓名或可识别信息。

## 10. 结果使用建议

完成 5–10 位测试后，先按任务查看完成率和耗时，再归纳重复出现的前三类问题。优先修复同时满足以下任一条件的问题：

- 导致任务失败；
- 让用户误以为已经执行或预订；
- 至少 3 位参与者重复遇到；
- 明显降低对推荐理由或异常恢复的信任。

简历中只能写实际完成的测试人数和真实结果。例如：“组织 8 名目标用户完成 5 项可用性任务，基于任务完成率与访谈反馈识别 3 类高频问题并完成两轮迭代。”在数据产生前不要提前写百分比。
